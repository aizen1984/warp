# 对抗验证协议（Adversarial Verification Protocol）

> **加载时机**：结论性产出验证时（code-reviewer 审查结论、planner RESEARCH/DESIGN-REVIEW、cc-api-analyzer aggregator）。派发一个独立验证 agent 做混合对抗验证（定向推翻 + 盲区扫描）。用户主动 `/cc-adversarial` 时走 `cc-adversarial/prompts.md` 的 challenger prompt（L1 / L2 单验证者）和假设提取，本文件是被动内嵌场景的协议。

---

## 目录

1. 一、适用范围（触发表、双条件门槛、跳过条件）
2. 二、核心原则

4. 四、结果处置（综合对比）

## 一、适用范围

| 触发点 | Skill | 验证对象 | 验证 agent 输入 |
|--------|-------|---------|----------------|
| 审查结论 | code-reviewer（阶段 11，降噪打分之后） | 问题列表 + 置信度 | 原始代码 + 变更范围 + **初始问题列表**（不含推理链，不含阶段 10 评分） |
| 研究发现 | planner RESEARCH 完成时 | findings.md | 原始需求 + 代码范围 + **初始 findings 结论**（不含推理链） |
| 设计评审 | planner DESIGN-REVIEW | 评审意见 | 设计文档 + 原始需求 + **初始评审意见**（不含推理链） |
| 接口分析 | cc-api-analyzer aggregator 阶段 | 表关系 + ER 推断 | 原始分析报告 + **初始 ER 推断**（不含推理链） |
| 通用方案产出 | 手动 /cc-adversarial 或 skill 内置（双条件判断） | 方案要点 | 原始需求/问题 + **方案结论**（不含推理链） |
| 分析/调研结论 | 手动 /cc-adversarial 或 skill 内置（双条件判断） | 分析结论 | 原始材料摘要 + **分析结论**（不含推理链） |
| 排查/诊断结论 | 手动 /cc-adversarial 或 skill 内置（双条件判断） | 根因判断 | 问题描述 + 已知线索 + **诊断结论**（不含推理链） |

**双条件门槛**。没有 Stop hook 自动调用，由用户手动 `/cc-adversarial` 或 Skill 工作流按下面两个条件自行判断。同时满足才触发，单一条件不触发，免得验证疲劳：

1. 数量条件：结论数 ≥3 条（1-2 条结论单条确认即可）
2. 不确定性条件：结论中含对冲用语（"应该"、"大概率"、"可能"）、涉及 trade-off / 方案选型、含跨模块 / 并发 / 事务场景，任一即算

例外：P0 关键词 + 核心改动（见 cc-adversarial/SKILL.md「高危关键词」一节）双条件不满足也触发。

### 跳过条件（低风险变更）

| 条件 | 说明 |
|------|------|
| 变更 LOC（改动行数）≤ 30 且单文件 | 影响面极小 |
| 纯 DTO/枚举/配置类变更 | 无业务逻辑风险 |
| 用户明确说"跳过验证" | 人工覆盖 |
| 文档/注释唯一改动 | 无行为变更 |

满足跳过条件但涉及 P0 关键词（`@Transactional`、`synchronized`、`DELETE`、`DROP`、支付/金融）时恢复完整验证。

## 二、核心原则

1. **混合对抗**：验证 agent 接收初始结论的结果（不含推理链），逐条复核找反例，收尾再检查未读文件和未覆盖区域补盲区。纯对抗（只推翻）会漏掉初始分析没覆盖的盲区，纯独立分析（同模型）容易产生相同偏见，混合兼顾两者。
2. **推理隔离**：验证 agent 只接收结论清单，不接收推理过程，防止推理链"说服"验证方。
3. **聚焦分歧**：最终输出重点放两方分歧点和盲区发现，共识点简要列出。
4. **验证质量保障**：验证 agent 要逐条判定初始结论（覆盖率 ≥70%）、给出收尾覆盖段落、列出已读文件；不满足视为验证无效，最多重派 1 次，仍不足则所有初始结论降为 medium-low 置信度。

## 三、验证 agent 规格

### 通用约束（嵌入验证 agent prompt）

> 本节 prompt 用于被动内嵌场景（code-reviewer / cc-planner / cc-api-analyzer 直接调用），subagent_type 用 `general-purpose`。用户主动 `/cc-adversarial` 时用 `cc-adversarial/prompts.md` 的 challenger-l2 prompt（含评分量表、P0 升级标记、对立假设），输出格式以各 agent 定义为准。两条路径用的 agent 不一样，不混用。

```
你是一个混合对抗验证 agent。你的工作流程：

**Phase A — 定向对抗 + 覆盖补充**：
你会收到初始结论的结果清单（不含推理过程）。逐条复核：
1. 对每个结论，问"这个结论在什么条件下会失败？"，然后去代码中验证
2. 找到反例 → 记录为"反驳"，附带代码证据
3. 找不到反例 → 记录为"确认"，说明你检查了什么
4. 对抗过程中发现相关但不在初始结论列表中的问题 → 记录为"关联发现"
5. 收尾步骤：检查初始结论中是否有你完全没读取相关文件的条目
   → 有：快速读取并给出判定
   → 无：检查是否有初始结论未覆盖的文件在变更范围内
      → 有：快速扫描，记录为"盲区发现"
      → 无：输出"无额外发现"

**信任边界反证（涉及输入校验责任时）**：
按 `shared-rules/minimal-change.md` 核对实际入口、入参契约、已有校验和异常传播。发现实际可达的未校验路径，或明确由本层承担的校验契约未满足时，才反驳原结论；已有可靠外层保护且本层无独立输入边界时，不因 public / 共享可见性、调用次数或假设调用方未来取消过滤而要求重复守卫。必要的外部输入、资源授权及业务不变量保护仍须保留。

**规则**：
1. 同一操作失败 2 次后换方法或标记失败并停止
2. 输出不超过 200 行，优先保留：反驳证据 > 盲区发现 > 确认共识
3. 校准与防偏（完整规则见 cc-adversarial/SKILL.md Gotchas）：推理隔离=只凭结论清单+原始材料判断，不接收推理链；文件范围限定=只读指定范围；株连校准=逐条独立评估，发现自己全打低分时重审一遍；否定偏差校准=判 ❌ 比例超 70% 时重审一遍

**判定三档**：❌ 有误（找到反例）/ ⚠️ 不完整（方向对但缺证据或漏维度）/ ✅ 确认（复核无反例）。

**输出格式**：
## Phase A: 定向对抗
| # | 初始结论 | 判定 | 问题/确认依据 | 建议行动 |
|---|---------|------|-------------|---------|
| 1 | [结论摘要] | ❌有误/⚠️不完整/✅确认 | [有误:错在哪+为什么 / 不完整:缺什么 / 确认:验证了什么] | [有误/不完整:修正或补充建议 / 确认:—] |

## 收尾覆盖补充
- [盲区发现 + 严重度P0/P1/P2 + 建议行动]
- [关联发现 + 建议行动]
- 无额外发现（如确实没有）

## 覆盖报告
- 已判定结论: #1, #2, #5, #7（N/M = X%）
- 未判定结论: #3, #4, #6（因 turn 不足跳过，列出原因）
- 读取文件: [列出已读取的文件]
```

### 场景化配置

| 场景 | max_turns | 验证重点 |
|------|-----------|---------|
| 代码审查验证 | 8 | 逐条对抗问题列表；收尾扫描未覆盖的维度/文件 |
| 其他场景（研究/设计/接口/方案/调研/诊断） | 6 | 对抗结论证据充分性；收尾扫描遗漏维度/文件 |

## 四、结果处置（综合对比）

匹配键按场景选：代码审查用 `文件:行号+维度`，接口分析用 `表名对`，其余用 `结论主题/要点`。对比结论描述、证据充分性、置信度。

| 情况 | 归桶 | 处理 |
|------|------|------|
| 双方一致确认 | ✅ 已确认 | 直接采用 |
| 验证方反驳（找到反例） | ❌ 有误 | 附: 错在哪+为什么+建议修正 |
| 验证方存疑（方向对但不完整） | ⚠️ 不完整 | 附: 缺什么+影响+建议补充 |
| 初始方发现 + 验证方未覆盖 | ⚠️ 不完整 | 标注"未经验证"，建议补充验证 |
| 验证方盲区发现 | 💡 盲区发现 | 附严重度+建议行动 |
| P0 分歧 | ❌ 有误 | 升级用户裁决，Lead 不自裁 |

P1 及以下的分歧可判定时 Lead 引代码证据裁决并说明理由，不可判定时标「待用户确认」。报告格式见 `cc-adversarial/templates/report-format.md`。
