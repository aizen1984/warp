# Legacy Change Policy — 存量行为保护与双路边界

> 需求是「给已经在跑的功能加新能力」时，先核对并复用现有配置和分发机制，保护存量行为，不为了统一新旧而重构老路。仅在确实需要双路且现有机制不足的原因已说明时，才适用下面的开关分支策略；不得据此自动新增开关、配置项、分支或名单。重写只在用户显式指定时才做。
>
> 加载时机：需求是给在跑的功能加新能力时读；cc-design 出技术方案、cc-planner 拆任务、cc-code-writer 派 Implementer 前各过一次。

Codex 执行时保留用户已有未提交改动，比较和搬运基于动手前的实际文件快照，不盲从 HEAD 复制覆盖。本文只约束真正影响既有业务路径的新能力接入；纯文档、技能适配和本次已授权的修复按豁免处理。需要双路时仍要验证分发、依赖与旧路径的关键行为，函数体没改不代表运行行为已验证；不按本文件自动执行 DDL、删数据或提交。
>
> 与全局 CLAUDE.md 工作原则 2 的关系：原则 2「最小必要变更」管改动范围与问题范围对等；本文件管同等范围内改老路还是绕开老路。两者正交，都要过。

## 一、触发识别与豁免

先按 [最小改动规则的业务配置约定](minimal-change.md) 核对 Confplus、配置表、配置类和完整调用链。现有机制足以表达本次需求时直接复用，不进入新增双路流程；以下双路检查只约束已确认需要的双路改造，不要求每次改动都生成 fork。

任一命中即需要检查存量行为保护：

| 信号 | 说明 |
|------|------|
| 目标文件有非本会话的 commit 历史 | `git log --oneline -3 <file>` 有记录且不是自己刚建的 |
| 用户提到「线上 / 生产 / 在用 / 每天用 / 已上线」 | 直接命中，不需要再找别的证据 |
| 需求措辞是「加一个 X / 支持 Y / 接入 Z」而不是「重构 / 重写 / 统一」 | 加能力 ≠ 授权改老实现 |
| 该模块有存量数据、历史记录、缓存表、监控 | 老路出错的代价不止一个报错 |

什么算「用户指定重写」：只有用户原话出现「重构这块 / 重写 X / 把新旧统一了 / 删掉老的」才算授权；「用新架构做 / 按新方式实现」是在描述新路长什么样，「支持一下 Y / 加个 X」和沉默都不算，按默认策略走并主动说明。

豁免（这些直接改老代码，不走双路）：

| 豁免项 | 为什么不走双路 |
|--------|--------------|
| 本会话新建的文件、纯文档 | 没有"在跑"这个属性 |
| 用户显式说了重写 / 重构 / 统一 / 合并 / 删掉老的 | 有授权 |
| 修 bug（老路本身就是这次要修的东西） | 双路等于把 bug 留在默认路上 |
| 安全补丁（注入校验、权限判断、越权修复） | 开关默认 false，做成双路 = 修复默认不生效，线上继续跑有洞的那条 |
| 依赖升级（尤其 breaking change） | 两条路 import 同一个库，物理上无法双路 |
| 补有证据的 null 守卫 / 前置条件校验 | 先按 [minimal-change.md](minimal-change.md) 确认实际输入或契约需要；豁免双路不等于授权预防性补守卫 |
| 加关键节点日志 / metric / traceId | 属"不可删清单"，排障没证据的代价高于改老代码的风险 |

豁免项照常适用「最小必要变更」：只改该改的那几行，不顺手重构邻接代码。

## 二、确需双路时的策略

```
已证明需要双路，且现有配置机制不足
   ↓
老路：git 里原样的代码，一字不改，开关关时逐字节执行它
新路：新架构自己一套，开关开时才走
开关：优先复用现有配置；确需新增时先说明最小方案，默认 false
```

为什么不是重写：老路在跑，重写它等于拿在用的功能赌新抽象没抽错，回归面是老功能全量。确需双路时重点验证配置读取和分发判断；还要沿实际依赖核对动态变化、空配置、非法配置及计算、写入范围，不能因老路函数体未改就省略受影响行为验证。

双路必然产生重复实现（老工具函数与新公共模块并存）。这份重复是有意支付的成本，不为了 DRY 把老路改成 import 新模块。

## 三、四条判据与四处检查面

四条判据只看老路文件自身的 diff，过了四条不等于没重写，还要过后面四处检查面。

| # | 判据 | 检查方式 |
|---|------|---------|
| 1 | 老路文件的函数体没有改动，只允许在函数开头加一行 fork | `git diff <老路文件>` 应只见 `if (!开关) return 老实现(...)` 这类单行 |
| 2 | 老路的函数签名 / 单例 / 导出符号没有变 | 改位置参数、删参数、改返回类型才算违反；末位追加一个默认为空的可选参数不算（老调用方一字不改、行为不变），但要在报告里点名 |
| 3 | 没有把老路一起抽进新的公共基类 / 公共工具 | 抽公共层把老路也改了 = 重写，这是最常见的伪装形式 |
| 4 | 老路的分支条件一个字都没动 | 见下方「分支条件」，最省事、最像"只加了一点点"、也最容易漏判 |

### 分支条件（判据 4 展开）

新场景不挤进老路已有的判断里，哪怕只多两个字符：

```java
// 不行：往老条件上挂一个 ||
- if (order.getStatus() == PAID) {
+ if (order.getStatus() == PAID || order.getStatus() == PRE_AUTH) {

// 不行：往老的 if-else 链里插一条 else if
  if (isDomestic(u))      { ... }
+ else if (isOverseas(u)) { ... }     // 插在老链子中间，改变了后面每条分支的到达条件
  else                    { ... }

// 不行：往老 switch 里加 case、往老三元表达式里套一层
```

```java
// 唯一允许的形态：方法最开头整条岔开，新场景的判断全写在新路里
  public Result handle(Order order) {
+     if (features.newFlow()) { return handleV2(order); }   // 老代码到此为止，下面一行没动
      if (order.getStatus() == PAID) { ... }
```

为什么单列：加一个 `||` 的 diff 只有几个字符，前三条判据全不响，但它改的是老路的判定逻辑。这种改动审查时无法证伪：站在 diff 面前证明不了存量数据里没有这个值，也证明不了将来不会有。一旦有，原本走 A 的输入就走了 B，回归面是老功能全量。

新增枚举值也不例外。最常见的抗辩是"这是本次新加的状态，老数据里不可能有"，要成立得有一次全量数据核对加一个"以后也不会有"的承诺，审查现场两样都拿不出。真要走这条，按「五、代价当面说清」说清理由，附上 `SELECT COUNT(*) FROM <表> WHERE <字段> = '<新值>'` 的实跑结果，然后等用户点头。

判据 4 不适用于豁免清单里的修 bug / 安全补丁 / 补守卫，那些本来就是冲着改判定逻辑去的。

### 判据管不到的四处检查面

下面四处一个字不碰老路文件，照样能把老路的运行时行为整个改掉。共同点是在一条正在跑的路中间加了一道新卡口：老路代码没改，昨天能过去的数据今天过不去了。判危不危险不看改了几行，看这张表、这个方法现在有没有人在用。

| # | 检查面 | 典型形态 | 怎么查 | 查到了怎么改 |
|---|--------|---------|--------|-------------|
| 5 | 老路依赖的共享模块 | 老路调的解析器 / 工具函数 / DTO 改了返回结构或语义 | 列出老路 import 的非标准库模块，逐个 `git diff` | 老函数签名与返回结构一字不动，老路继续吃老结构；新需求另写一个函数（`parse_result_v2`）或另开模块。不给共享函数加开关，那等于把 fork 塞进最下层 |
| 6 | 配置装配层 | 老路读的配置项换了来源、加了默认值、被新配置段覆盖 | `git diff` 配置类 + 逐个核对老路读的每个 key 取值是否变了 | 保留既有来源、默认值和优先级；已有配置语义能表达需求时复用，不能为隔离新旧另建同义配置或静态名单。确有缺口时先说明原因与最小方案，不静默改变旧 key 含义 |
| 7 | 数据层 / 表结构 | 加 NOT NULL 列、改唯一键、加索引、DROP 重建 | 加列前先 `SELECT COUNT(*) FROM <表名>;` 看表多大要锁多久；加唯一约束前先 `SELECT <约束列1>, <约束列2>, COUNT(*) AS cnt FROM <表名> GROUP BY <约束列1>, <约束列2> HAVING COUNT(*) > 1;` 看有没有重复；老路的每条 SQL 拿到新表结构上实跑一遍，尤其 WHERE 没带新维度时会不会读到别的维度的数据 | 加列带默认值：`ALTER TABLE <表名> ADD COLUMN <列名> <类型> NOT NULL DEFAULT <默认值> COMMENT '<业务含义>';`，老路的 `INSERT` 和 `SELECT *` 真跑一遍；加了新维度进唯一键时，老路的 WHERE / DELETE 也带上该维度（否则读串、删串），或在开关关闭时清掉非默认维度的行；查出重复数据的先说清怎么处理再谈加约束，没重复的也要 grep 所有写入点看撞上 `DuplicateKeyException` 怎么办（当写成功 / 忽略 / 转业务错误码三选一）。这一处必须实跑验证，不接受推理 |
| 8 | 老路调用的方法新增抛异常 / 新增校验 | 在共享方法、校验器、拦截器、切面里加 `throw`；或给已有参数加非空/格式校验 | 沿完整调用链核对已有校验、异常传播和统一处理；重点查依赖 null、空列表或默认值继续执行的旧分支 | 按已核对契约补必要保护，保留原返回和错误语义；不能仅因直接调用方没写 catch 就新增兜底、改成 `Optional` 或吞错返回成功。「以后调用方都会改」不能作为兼容证据 |

这四处一旦命中，判定与四条判据同级，不因为"老路文件一个字没改"就降级。检查面 7 有实测教训：给缓存表加数据源列并进唯一键后，老路的两条 SQL 都串了维度。`SELECT ... WHERE database_name=? AND table_name=?` 把另一个数据源的行一起读出来；`DELETE` 把另一个数据源的缓存一起删掉。四条判据全过，老路行为已经错了。

最常听到的两句话：「表里不可能有那种数据」要拿上面那条 `GROUP BY ... HAVING` 的实跑结果回；「调用方以后都会改的」要拿改完的 diff 回。说了不算，跑了才算。加列、加约束、抛异常在生产库上都不好反悔，按全局 CLAUDE.md「可逆性优先」动手前先跟用户确认。

### 违反了算多重（分档，审查与自检共用一把尺）

| 档 | 什么情况 | 动作 |
|----|---------|------|
| 阻断 | 改到老路的判定逻辑或数据形状：判据 4（分支条件）、判据 1（函数体）、判据 2 的位置参数/返回类型/单例、判据 3（抽基类）、检查面 5/6/7/8 | 停手，回退成双路；未授权不提交 |
| 点名不阻断 | 违反但向后兼容且回归面可枚举：末位追加默认为空的可选参数、纯新增的入口/方法/文件、只加不改的配置项 | 照常提交，但在报告里逐条点名，让用户看见 |
| 不报 | 命中「触发识别与豁免」里的豁免（修 bug / 安全补丁 / 依赖升级 / 补守卫 / 加日志 / 纯文档 / 已授权） | 不提，只受「最小必要变更」约束 |

分档只看"改到哪儿"，不看"改了几行"：一行的 `||` 是阻断档，三十行的纯新增方法是不报档。

## 四、开关放哪一层

判据是老路逻辑实际所在的那一层，不是数 fork 点。沿调用链找老路业务逻辑真正待着的那一层，只有那一层的函数体能被整段搬走、保持逐字节不变。

| 位置 | 评价 |
|------|------|
| 最上层（每个 HTTP 入口 / Controller 方法） | 不选：这层通常只是转发，在这里 fork 挡不住下游被改；且入口有几个就要改几处 |
| 老路逻辑所在层（多数项目是 service） | 默认选这里：函数体整段搬为 `_xxx_legacy`，原函数只剩一行 fork |
| 最下层（client / DAO 内部按开关拼参数） | 不选：新老逻辑挤进同一个函数体，等于重写 |
| 新老共用的工具 / 解析 / DTO 模块 | 永远不在这里 fork，见检查面 5 |

别用"fork 点最少"当理由：实测反例，某项目 service 层 `get_client` 调用点 7 处、HTTP 入口 8 个，数量相当按"最少"选不出来；有的入口会绕过 service 直接取依赖，那一处无论如何都得单独 fork。层选对了，fork 点多几个也认。

老路函数体的搬运要求：以动手前实际文件快照为准，原样复制进 `_xxx_legacy`，除函数名外 diff 为空；HEAD 仅在已核对该段工作树无既有改动时作参照，不覆盖用户未提交内容。不顺手改命名、合并分支、补注释。

### 多轮迭代：只保护最初那条老路

第二次、第三次迭代要改的如果是上一轮自己加的新路，本规则不再叠加。新路虽然也有了 commit 历史，但没有"在跑的存量用户"这个属性，直接改，不再 fork 一层。否则三轮下来同一个方法会变成四份实现、八种开关组合，哪种组合真跑过无人负责：

```python
# 规则被误用成这样就是坏了
if not features.a: return _legacy(...)      # 迭代 1
if not features.b: return _v1(...)          # 迭代 2 又不敢改 _v1
if not features.c: return _v2(...)          # 迭代 3
```

判断标准：这条路上有没有真实用户在跑。老路有 → 保护；上一轮刚加的新路、开关还没打开过 → 直接改。

## 五、代价当面说清

提出双路方案时，同一条消息里写清三件代价：① 产生哪些重复实现 ② 老路会长期躺在仓库里 ③ 收口时机。收口时机指新路稳定跑够一段时间 + 用户明确说可以删老路，那时才是重写的时机，且仍要用户拍板。

反过来，这次也可能确实该重写：老路本身就是这次要修的 bug 源，或者老路已无人调用。这种时候说清理由后仍要等用户点头，不自行动手。

## 六、反例（2026-08-24）

需求：SQL IDE 工具接入海外数据源（原本只有主营一个）。实际做法：把天天在用的 `MokaClient` 拆成 `BaseQueryClient` 基类 + 子类，`get_tables()` 签名从 `(database)` 改成 `(instance_name, schema_name)`，单例 `get_moka_client()` 删除，前端 store 从 `databases[]` 改成 `databasesByDs{}`，合计 31 文件、+1106/−670。用户只说了「接入海外」，没说过重写主营，主营回归面从 0 扩到全量。四条判据里违反了三条：判据 1（函数体大改）、判据 2（签名变更 + 单例删除）、判据 3（抽公共基类把老路一起改了）。

正确做法：老 `moka_client.py` 原样不动，新架构的主营实现另开一个文件；`schema_service` / `database_service` 的公开方法开头加一行 fork，老路函数体整段搬为 `_xxx_legacy`；配置加 `features.multi_datasource`，默认 false。这次改动里 service / router / api 层「多一个默认为空的可选参数」是向后兼容的，不构成重写。判重写按文件分层看：不因总 diff 大就全盘否定，也不因大部分兼容就放过真正被改写的那几个文件。
